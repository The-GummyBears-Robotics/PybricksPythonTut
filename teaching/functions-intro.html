≈5 min Part 2 — You already call functions

Same rule everywhere: a name, parentheses, and sometimes values inside — that is a call.

Calling looks like wait(1000), hub.light.on(Color.RED), robot.straight(400), or sensor.distance(). Someone else wrote those recipes; your job in lesson 9 is to write your own recipes with def.

Calls with a dot, like hub.light.on(...), are methods — functions tied to an object (hub, a motor, a sensor). You still read them as “name, parentheses, maybe values,” just with the object written first.

When a program gets long, it gets hard to fix. Splitting the robot’s job into named behaviours you can read from top to bottom is the same trick in block coding or in Python — you are about to learn the Python side with def.

≈12 min Part 3 — Writing your own: def, parameters, return

Vocabulary + two small examples, then you connect to the 9-functions/ folder on the hub.

What is a function?

A function is a reusable block of code with a name. You write the steps once, then run them again by calling that name — instead of copying and pasting the same instructions everywhere.

If you have used block coding, a Task (or “My Block”) bundles several actions under one short name — and nothing inside runs until the main program calls that name. Text Python matches that: def stores the recipe (the indented block); calls elsewhere in the file choose when it runs. In blocks you might pick an icon so the task is easy to spot; in Python the readable function name plays that role — pick short names that say what happens (blink_party, not bp). Keep each chunk small enough to explain in one breath, and add a docstring ("""…""") or comments so a teammate can read the plan at a glance.

Without functions: copy-paste the same code in many places. When you change one detail, you hunt for every copy.
With functions: write the recipe once, give it a clear name, call it whenever you need it.

Before / after: copy-paste mess vs one function

Imagine the same short welcome flash on the hub — a beep and a green LED — whenever the day calls for it: judges enter, driver practice, match reset, finals, trophy photo. If you copy-paste the same lines every time, the file grows fast — and when you change the beep length or LED timing, you must hunt every twin block. Toggle to see the same story with one def and many short calls (same spirit as 1-hub/ light + sound, just grouped).

Each movement, sensor check, or hub habit can live in its own named chunk — then your main program reads like a checklist of robot moves instead of one wall of code.

Starter celebrate() (minimal version)

Tiny celebration: one beep and a solid green LED, then call celebrate() several times. On a real hub you need imports for PrimeHub and Color. The Demo 1 simulation tab matches the longer fun-base.py (icon, play_notes, blinking). 

from pybricks.hubs import PrimeHub
from pybricks.parameters import Color

hub = PrimeHub()

def celebrate():
    hub.speaker.beep(500, 200)
    hub.light.on(Color.GREEN)

# Call it as many times as you want
celebrate()
celebrate()
celebrate()

Four parts make every function

Every def line has the same anatomy. Here is how the parts show up on def celebrate2(freq, length)::

PartWhat it is
defKeyword that starts a definition.
celebrateFunction name — choose something that says what it does.
(freq, length)Parameters — placeholders the caller fills in (here: frequency and length of the beep).
indented bodyThe lines that run when you call the function (speaker + light, etc.).

Naming: drive_square() reads better than ds().

def celebrate():
    hub.speaker.beep(500, 200)
    hub.light.on(Color.GREEN)

def celebrate2(freq, length):
    hub.speaker.beep(freq, length)
    hub.light.on(Color.GREEN)

celebrate()
celebrate2(250, 100)

Fuller celebrate() (like 9-functions/fun-base.py)

Here is a bigger celebration: show a happy icon, play a short tune with play_notes, blink the hub light, wait, then turn the LED off — and call celebrate() more than once. That is the same pattern as 9-functions/fun-base.py on the hub. 

from pybricks.hubs import PrimeHub
from pybricks.parameters import Icon, Color
from pybricks.tools import wait

hub = PrimeHub()

def celebrate():
    """Play a celebration animation."""
    hub.display.icon(Icon.HAPPY)
    hub.speaker.play_notes(['C5/8', 'E5/8', 'G5/4'], tempo=150)
    hub.light.blink(Color.GREEN, [200, 200])
    wait(2000)
    hub.light.off()

# Call the function
celebrate()
wait(500)
celebrate()  # Call it again!

Syntax patterns

Write thisMeaning
def name():Define a function with no parameters.
def name(param):One parameter.
def name(a, b):Multiple parameters.
return valueSend a value back to the caller (try Demo 3).
name() or name(1, 2)Call the function (with or without arguments).

Functions also help you keep programs cleaner, easier to debug, and easier to change later — especially when the robot must do the same behaviour in more than one place.

Order of execution: when Python reaches a line like celebrate(), it runs the whole function body, then comes back and continues with the next line after the call. So setup code above still runs first; lines below wait their turn — same “print before → call → print after” rhythm many function tutorials use on paper.

Parameters (inputs in parentheses)

Values you pass in are arguments; the names in the def line are parameters. Those parameter names are local: they only mean something inside that function while it runs (like scratch paper that disappears when the function finishes). Same idea as blink_times(n) on the simulator and beep_times(count, frequency) in 9-functions/fun-inputs.py. Hub LEDs: 9-functions/fun-blink-pattern.py.

return (hand a value back)

The caller can use the result in an if or save it in a variable — like too_close(...) in 8-sensors/distance-avoid.py. More examples: 9-functions/fun-returns.py, 9-functions/fun-sensor.py, 9-functions/fun-distance-threshold.py.

Extra (optional): math class ↔ return

In algebra you might write f(3) and get a number out. Python’s return is the same idea: the function hands a value back to the expression that called it. Example: def square(x): return x * x then square(3) produces 9 for the rest of the line to use.

Extra (optional): how many parameters is “just right”?

Imagine turns: a block that only does “90°” is quick to use, but you end up duplicating tasks for 45°, 30°, … A single turn_degrees(angle, speed)-style function covers many cases with one recipe. Loading every rare option (coast, brake, timeout, …) into one giant header can be harder to read than it’s worth — aim for enough inputs to reuse the code, not every knob in the universe.

Extra (optional): scope — why a name can “disappear”

Variables defined outside a function are global (visible in many places). Parameters and names you assign inside the function are local. After the call ends, a parameter like x is not a legal name in the outer program — using it there causes a NameError. 

y = 7

def f(x):
    print(x)   # 4 — the argument copied into x
    print(y)   # 7 — global y is still visible here

f(4)
print(y)       # 7
# print(x)     # NameError: x only existed inside f()

Quick tips (keep these six in mind first)

  1. Descriptive names — drive_square() beats ds().
  2. Naming style — Pybricks samples usually use snake_case (turn_degrees). Some lessons use camelCase (turnDegrees). Either can work; stay consistent in one file.
  3. Docstrings — """What this does.""" under def.
  4. Parameters — one function, many cases.
  5. return — for answers used in if / math.
  6. Defaults — optional args, e.g. def blink_times(n, ms_on=500):
More tips (if you have time)
  1. Smaller functions — easier to test than one giant file.
  2. Composition — one function can call another (build big behaviour from small pieces).
  3. Trace one chunk — when something breaks, run or print inside one function at a time so you see whether that piece is wrong (same “trace the steps” idea as Pybricks’ square task exercises).
  4. Helpers — repeat beeps / LED patterns once.
  5. Slow vs fast setups — two tiny functions can apply different drive settings mid-run (acceleration / speed) without duplicating whole missions.
  6. Don’t recurse by accident — a function that keeps calling itself can exhaust the hub; use a normal loop for “repeat forever” unless a mentor teaches recursion on purpose.
  7. State machines & DRY — tidy big drivers; don’t repeat yourself.
  8. Built-ins — Python already ships helpers like abs, max, min, round, len (useful on lists/strings). They are plain calls: max(a, b), not magic.
